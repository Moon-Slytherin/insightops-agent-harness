# 用人话理解 AgentHarness Lab

## 这到底是什么程序

它不是另一个负责聊天的 Agent，也不是 Productboard 一类完整商业产品。它是 **Agent 外面的运行程序**。

可以把大模型想成一个会思考、但不能直接操作数据库的员工。Harness 相当于员工所在公司的工作系统：把任务交给员工，提供经过批准的工具，检查参数，记录每一步，限制最多做几步，失败后保存进度，并在最后组织考试。

没有大模型时，离线 `demo` 模式不是智能 Agent，只是一个按照固定剧本行动的替身。它的作用是让开发者在不花 API 费用、模型输出不随机的情况下测试运行系统。DeepSeek 模式才会让真实模型自行决定调用什么工具。

## 谁会使用

- **Agent 开发者**：把业务工具接入运行时，并调试模型为什么选错工具；
- **测试/评测工程师**：设计案例，检查工具选择、证据、拒答和异常恢复；
- **平台工程师**：关注任务状态、检查点、并发处理和事件轨迹；
- **业务人员**：只使用演示页面提出事故调查问题，不直接配置 Harness。

## 一次任务怎样运行

1. 用户提交问题，程序生成 `run_id`，把初始状态写入 SQLite；
2. 模型读取问题与工具说明，返回文字或结构化工具调用；
3. Harness 检查工具是否在白名单、参数是否符合 JSON Schema；
4. 工具从本地统计数据或事故文档读取证据；
5. Harness 保存工具结果，并将结果送回模型继续推理；
6. 模型给出最终答案；程序检查明显数字矛盾后才发布；
7. 每一步都形成事件，评测器检查整条轨迹而不只是最终文字。

如果进程在第4步后停止，SQLite 中已经保存的结果仍在。重新调用 `resume` 时，程序从未完成的步骤继续，不必从头再问模型。

## 两种“测试”不要混淆

- **Pytest** 测代码：例如参数错误是否被拒绝、两个 worker 会不会同时处理同一任务；
- **Agent Eval** 测行为：例如模型有没有选对工具、是否根据证据回答、数据不足时有没有乱猜。

因此“44条测试通过”和“真实模型19/20”不是同一个指标，也不能相互替代。

## 为什么它不是纯 Toy

它已经接入真实模型并暴露过真实失败：第一次回答出现“新增13条里有16条”的矛盾；后续评测发现工具过度调用和评测器误判。项目不只展示成功页面，还实现了检查点、租约、失败恢复、轨迹和可复现评测，并保留失败案例。

但它也不是生产系统：数据规模小、工具只有两个，没有鉴权、沙箱、人工审批和分布式任务系统。准确的说法是：**它是一个经过真实 API 和故障案例验证的工程型原型。**
