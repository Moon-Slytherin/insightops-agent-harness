# 真实 DeepSeek 调用：首轮失败与改进

## 已观察到的事实

第一次真实调用返回空正文的 HTTP 400，运行停在 `rounds=0`、`tool_calls=0`。诊断发现当前终端中的 `DEEPSEEK_API_KEY` 长度只有 1，而完整密钥长度为 35 且以 `sk-` 开头。使用剪贴板原始文本重新设置环境变量后，请求成功完成：`status=completed`、`rounds=2`、`tool_calls=2`，模型自主调用了 `payment_metrics` 和 `search_incident_docs`。

因此，不能把最初的 400 归因于模型或工具协议；已经证实的直接原因是密钥注入错误。运行时随后增加了密钥格式预检查，让截断密钥在发起网络请求前失败并给出可理解的错误。

## 模型回答中的真实失败

工具结果为：上期 5 条、本期 18 条、其中 3.2.1 版本 16 条。模型先正确列出这些数字，随后写出“本期新增的 13 条投诉里，16 条落在 3.2.1”，产生了子集大于总数的内部矛盾。正确关系是“本期 18 条中，16 条来自 3.2.1”；新增量 13 不能作为这 16 条的分母。

这个问题说明“调用了正确工具”和“回答包含真实数字”仍不足以保证最终结论可靠。系统新增确定性数量关系校验：发现“X 条中/里有 Y 条”且 `Y > X` 时拒绝发布答案，把具体问题反馈给模型重写；第二次仍失败则暂停任务，不向用户返回错误答案。相关测试覆盖发现、修正成功和重复失败三条路径。

## 目前能声称的验证结果

- 已完成一次真实 DeepSeek 端到端工具调用；
- 已发现一例真实的数值关系错误；
- 新增的防护通过离线自动测试；
- 防护加入后的真实 DeepSeek 自动重写效果仍需再次调用验证。

一次成功运行不能代表模型准确率。后续需要在独立案例集上报告工具选择、工具执行、证据一致性和最终任务成功率。
