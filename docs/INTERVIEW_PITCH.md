# Agent Harness 岗位面试讲述稿

## 30秒版本

我实现了一个可恢复、可观测、可评测的多工具 Agent 运行时，并用支付事故调查作为演示任务。运行时自己负责模型与工具的多轮循环、Pydantic 参数校验、只读白名单、SQLite 检查点、超时重试、执行预算、并发租约和事件轨迹。项目接入了 DeepSeek 真实 API，并用20条场景评测工具选择、证据和拒答行为；最终复核通过19条，同时保留一个模型未检索文档就错误拒答的真实失败案例。

## 哪些是模型/API提供的，哪些是我实现的

DeepSeek/OpenAI API 提供语言推理和 Function Calling 输出。工具是否允许执行、参数是否合法、怎样重试、状态存在哪里、进程重启后如何恢复、两个 worker 如何避免重复处理、轨迹记录和评测规则，都是 Harness 自己实现的。离线 DemoModel 只用于确定性回归，不当作真实模型能力。

## 最值得讲的失败案例

第一次真实 DeepSeek 调用成功选择了统计和文档工具，但最终写成“本期新增13条投诉里，16条来自3.2.1”。工具结果正确，错误发生在模型综合阶段。我增加了发布前确定性校验：发现子集大于总数时拒绝答案，把问题反馈给模型重写；第二次仍错则暂停而不是发布。自动测试覆盖了“拒绝—重写成功”和“连续失败后暂停”。

随后20条真实评测又发现两类问题：模型会过度调用工具；评测器只认“条”而误判“起”和 Markdown 表格。我完善了工具能力边界和最小必要调用规则，也给评测器增加等价表达测试。这个过程让我意识到评测器本身同样需要回归测试。

## 为什么不用 LangGraph

这个项目目标是理解 Harness 的底层职责，因此直接实现最小循环和状态持久化，能明确说明每次模型调用、工具执行和 checkpoint 的边界。若业务复杂到需要大量分支、可视化编排或成熟生态，再引入 LangGraph；当前规模下自行实现更便于展示运行机制。

## 已知不足怎么回答

当前只有两个只读工具，工具仍按顺序执行，数据是模拟数据；没有实现 SSE、MCP、Sandbox、HITL 和生产鉴权。SQLite 租约经过自动测试，但没有做多进程压力测试。下一步若继续工程化，我会优先做并行只读工具执行、请求取消和生产级观测，而不是先堆更多业务 Agent。
