# DeepSeek 真实评测：第一次基线与故障分析

评测日期：2026-09-23
数据集：项目自建的 20 条支付事故回归案例（不是公开 Benchmark）
模型模式：DeepSeek 真实 API

## 原始结果

- 严格整题通过：8/20（40%）；
- 运行完成：20/20；
- 工具执行成功：20/20；
- 工具选择符合预期：12/20；
- 关键事实命中：16/20；
- 拒答/因果边界：20/20；
- 数字一致性：20/20；
- 虚假前提与越权请求处理：20/20。

## 人工复核发现

`required_facts` 的 4 次失败是评测器误判，不是模型事实错误：模型使用了“18 起”“16 起”或 Markdown 表格中的裸数字，而第一版规则只接受“18 条”这种表达。扩展等价计数表达后，在不改变模型答案的情况下，校正后的严格基线为 **12/20（60%）**。

这说明评测器也属于需要测试的软件。只看一个总分会把模型问题和裁判问题混在一起，因此报告保留了每项检查和完整回答。

## 确认的主要模型问题

剩余 8 个失败全部来自工具选择：

- 只问增长率，却额外检索文档；
- 只问发布说明或手册，却额外查询统计；
- 对退款到账、会员开通、错误码、平台拆分和安装量等工具明确不覆盖的问题，仍调用一个或两个工具确认。

工具调用都执行成功，最终回答也正确承认数据不足，但无关调用增加延迟、Token 消耗和系统负载。对 Agent Harness 来说，这是效率和路由精度问题，而不是单纯的“答案对不对”。

## 修复

1. 工具描述改为明确的能力边界，列出能返回和不能返回的数据；
2. 系统指令增加“最小必要调用”规则，禁止为补充背景而顺带调用无关工具；
3. 评测器接受“条/起/次”和 Markdown 表格等价表达；
4. 第二轮报告新增模型响应耗时和 Token 用量，便于比较优化是否真的减少成本。

## 第二轮复核

加入能力边界和“最小必要调用”规则后，报告原始结果为 13/20。人工复核再次发现两个裁判问题：加粗 Markdown 表格中的 `**18**` 未被数字规则识别；“不在工具范围内”未被拒答规则识别。修正后第二轮校正成绩为 **15/20（75%）**，工具选择也为 15/20。

剩余 5 个失败来自路由过度收缩：模型在需要验证用户数字前提或建立证据链时没有调用工具；另有一次明知工具无平台维度仍进行了查询。第三版把路由规则改为按“数字、文档、综合取证、验证前提、范围外问题”明确分类。

所有轮次继续使用相同的 20 个问题。评测规则的调整均来自可复现的误判并记录在本文中；没有删除困难案例。`missing_platform_breakdown` 曾由“两工具”修正为“仅文档检索”；最终复核确认问题只问能否得到平台结论，而工具契约已经明确没有平台统计，因此直接说明证据不足即可，最终期望为不调用工具。

## 最终轮与停止条件

第三轮原始报告为14/20。逐题人工复核发现5个新的确定性裁判误判：Markdown表格中的加粗版本计数、两种“不构成因果”的表述、在否定句中复述“500条”的虚假前提，以及把“无平台统计”问题强制要求为文档调用。修正规则后，对同一份已保存回答执行离线 `--rescore` 得到 **19/20（95%）**：运行完成20/20、工具执行20/20、工具选择19/20、关键事实19/20、政策边界20/20、数字一致性20/20。

唯一保留的真实失败是 `causal_trap`：模型没有调用工具，并错误声称发布文档中不存在 SDK 5.8.0。项目在此停止继续调 Prompt，不追求20/20，以保留可分析、可回归的失败案例。最新保存报告的模型调用总耗时为49.99秒，总Token为31,173；这些数字来自本次20条项目案例，不能外推为生产性能。模型输出存在随机性，19/20只描述这次已保存并复核的运行，不代表稳定线上成功率。
