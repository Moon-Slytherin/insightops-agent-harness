# 项目运行与验证入门

## 项目在做什么

支付事故是演示题。真正要展示的是一个 Agent 运行时：接收问题，调用模型，按模型要求执行允许的工具，保存每步结果，遇到故障时继续或暂停。`backend/app/harness/runtime.py` 是流程负责人；`model.py` 是模型接口；`tools.py` 是工具白名单；`store.py` 把进度和事件写入 SQLite。

离线演示用 `DemoModel` 按固定规则发出工具调用，它能让我们重复验证运行时，但不能回答“真实大模型是否足够聪明”。`OpenAIResponses` 才会请求真实模型，需要你自己的有效 API 密钥。

## 用一次调查理解关键名词

1. **工具调用**：模型说“我要查支付投诉统计”，并给出工具名和参数；程序校验参数后执行只读工具。
2. **检查点**：将当时的提问、模型输出和工具结果保存到 SQLite。程序重启后，从最后一次已保存的进度继续。
3. **事件轨迹**：记录什么时候调用模型、调用哪个工具、有没有重试。可以回看过程，帮助定位错误。
4. **租约**：某个处理者取得一段时间的运行权。第二个处理者同时恢复该任务会收到 HTTP 409。处理者退出后，租约到期，其他处理者才能接管。即使旧处理者后来醒来，也不能写入新检查点。
5. **预算**：模型轮数与工具调用数都有上限，避免无限循环。

一个细节：工具超时会触发重试，但当前使用的线程无法被强行停止。因此工具目前只有读取功能。以后若增加“发邮件、改订单”等写操作，还必须设计外部幂等机制，不能直接套用现在的重试方式。

## 三种验证分别证明什么

| 命令或操作 | 检查什么 | 不能证明什么 |
| --- | --- | --- |
| `python -m pytest -q` | 26 条自动测试，包括恢复、并发互斥、数据库连接关闭、接口状态码、伪造数字与缺失工具结果 | 大模型答案在真实问题上的准确率 |
| `python -m backend.app.harness.eval` | 4 条固定脚本模型场景，检查状态、工具结果、答案中的数字和文档路径 | 真实模型的成功率或任意结论的真实性 |
| `python -m backend.app.harness.smoke_openai` | 在你本机用有效密钥实际请求模型、执行两种工具并打印答案 | 在更多问题上的正确率；答案仍需核对原始证据 |

真实 API 冒烟检查只有实际联网运行成功才能记录为“已验证”。旧版规则接口的 11/12 是另一套题目，不能与上述 4/4 合并或比较。

`evidence_match` 是有限的格式检查：核对答案中写出的“几条投诉”、增长率、版本号和文档路径与工具结果是否相符。它不能理解所有中文因果关系，也不能替代人工核查。测试中的“新增 99 条”故意不在数据里；评测正确地将它判为失败。

## 你可以亲手验证恢复

先用 `python -m pytest -q tests/test_harness.py -k model_error_pauses_and_later_resumes -v` 运行单个测试。它让一个假的模型先失败两次：系统将任务标成 `paused`；再次调用 `resume` 后，模型返回结果，任务进入 `completed`。这验证的是恢复代码，不需要网络和 API 密钥。

再运行 `python -m pytest -q tests/test_harness.py -k two_workers_cannot_resume_the_same_run_at_once -v`：第一个处理者暂时停在模型调用中，第二个处理者尝试恢复同一任务，得到 `RunBusy`，随后第一个处理者完成。这个测试由同一测试进程里的两个独立 `RunStore` 实例模拟两个处理者；真实多进程压力仍待验证。

在 Windows PowerShell 的项目目录，先执行 `conda activate insightops`。如果解压在新目录，确认该环境已安装依赖；然后执行上述命令。每次改代码后，只重跑与你改动相关的测试，再跑完整 `python -m pytest -q`。
